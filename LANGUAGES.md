# Languages Used in Incident-Zero

Incident-Zero (I-ITSM) is a **Java-first** project. The whole domain core, the incident lifecycle, SLA math, assignment, audit ledger and the AI gateway, is written in Java. Other languages appear only where Java is either impossible (the browser, the database engine, the OS shell) or clearly the wrong tool (training ML models, quick automation scripts).

This document lists every language in the repository, where it lives, what it does, and why we picked it over Java for that part.

## 1. Java: the core of the system

**Where:** `backend/` (Maven project `incident-zero-backend`, package `edu.campus.iitsm`).

**What it does:**
- The 11 Spring Modulith modules: `incident`, `sla`, `assignment`, `audit`, `intelligence`, `intake`, `knowledge`, `catalog`, `identity`, `notification`, `shared`.
- The sealed `IncidentState` hierarchy (10 lifecycle states) and the command → transition rules.
- Priority strategies (ITIL matrix, product score, weighted score), dual pause-aware SLA clocks, business-calendar arithmetic, escalation chain.
- Seven assignment strategies including the Hungarian (Kuhn–Munkres) batch matcher.
- The SHA-256 hash-chained audit ledger.
- The AI gateway (PII redaction, prompt guard, semantic cache, schema validation, rate limit, circuit breaker), and **in-process inference** of the embedding and SLA-risk models through ONNX Runtime.
- REST API, SSE live feed, JWT security, email notifications.
- Tests: JUnit 5, ArchUnit (rules R1–R9), Spring Modulith `verify()`, and the pure-JDK state-transition harness.

**Why Java:** strong static typing, sealed classes and records for modelling the state machine, a mature ecosystem (Spring Boot, Spring Modulith, Flyway, Resilience4j, Bucket4j, ArchUnit) and compile-time enforcement of the architecture. This is the "deterministic domain core" that every other part of the system depends on.

## 2. Python: offline ML training and helper scripts

**Where:**
- `ml/train_sla_risk.py`: trains the SLA breach-risk model.
- `scripts/`: `run_backend_demo.py`, `setup_env.py`, `demo_db_helper.py`, `reset_demo_load.py`, `run_mvn_test.py`, voice/demo helpers.
- `tools/readme-art/build.py`, `px.py`: generate the pixel-art SVGs in `docs/readme-assets/`.
- `tools/split.py`: extracts `// FILE:` segments from the master implementation markdown into real source files.

**What it does:** trains a calibrated gradient-boosted classifier (scikit-learn `HistGradientBoostingClassifier` + `CalibratedClassifierCV`) on synthetic incident data and exports it to **ONNX** with `skl2onnx`. The Java backend then loads that `.onnx` file and runs it in-process. The other scripts read `.env`, prepare the demo database, launch the backend, and draw README graphics.

**Why not Java:** the ML ecosystem (NumPy, pandas, scikit-learn, skl2onnx) only exists properly in Python; doing the same training in Java would mean reinventing these libraries. Python is used **offline only**: at runtime nothing calls Python, and the model is served by Java via ONNX. For small glue scripts, Python is faster to write and needs no compile step or Maven project.

## 3. JavaScript (Node.js): automation around the frontend and API

**Where:**
- `scripts/demo-seed.mjs`: logs in and creates the demo tickets through the real REST API.
- `scripts/e2e_lifecycle.mjs`: end-to-end lifecycle verification ("Gate A") against the running Spring Boot API.
- `scripts/deploy-pages.mjs`: builds the frontend and publishes it to the `gh-pages` branch.
- `scripts/run_ui_audit.mjs`, `frontend/run_ui_audit.mjs`: Playwright-driven UI audit screenshots.
- `frontend/tailwind.config.js`, `frontend/postcss.config.js`: build tool configuration.

**Why not Java:** these scripts sit next to the frontend toolchain (Vite, Playwright, npm), which is Node-based. Node is already installed for the frontend, `fetch` is built in, and one `.mjs` file runs the same on Windows, macOS and Linux. A Java equivalent would need its own build setup for a script of a few dozen lines. Tailwind and PostCSS only accept JavaScript config files.

---

## 4. HTML: the page shells

**Where:** `frontend/index.html`, `frontend/app.html`, `frontend/public/landing.html`, `landing.html`.

**What it does:** `index.html` / `app.html` are the entry documents Vite injects the React bundle into. `landing.html` is a static landing page for GitHub Pages.

**Why not Java:** browsers only render HTML. Java has no role in the browser; the backend only serves JSON and SSE.

---

## 5. TypeScript / TSX: the React frontend

**Where:** `frontend/src/` (`App.tsx`, `main.tsx`, `pages/{stage,portal,workbench,admin,specs}`, `components/`, `context/`, `services/api.ts`, `commands.ts`, `mappers.ts`, `sound.ts`, `pixelSprites.tsx`, `types/`), plus `vite.config.ts`, `playwright.config.ts`, `e2e/lifecycle.spec.ts`.

**What it does:** the five "ROM cartridge" workspaces, the React Flow dependency graph, the Three.js / React Three Fiber campus scene, Web Audio sound effects, the typed API client and the Playwright tests.

**Why not Java:** code running in the browser must be JavaScript (or compile to it). TypeScript gives us Java-like static types on top of JavaScript, so the DTOs coming from the Java API are typed on both sides. Java-to-browser options (GWT, TeaVM, Vaadin) would cut us off from React, Three.js and React Flow.

---

## 6. CSS (Tailwind)

**Where:** `frontend/src/index.css`, `frontend/tailwind.config.js`.

**What it does:** the arcade theme, colours, typography (Space Grotesk, JetBrains Mono), tabular numbers for SLA timers.

**Why not Java:** styling in a browser is CSS; there is no alternative. Tailwind keeps styles close to the components.

---

## 7. SQL (PostgreSQL)

**Where:** `backend/src/main/resources/db/migration/`
- `V001__reference_tables.sql`: services, categories, users, reference data.
- `V002__incident_core.sql`: the `incident` table with `CHECK` constraints, sequences, vector and full-text columns.
- `V003__audit_timers_ai.sql`: audit ledger, SLA timers, `ai_suggestion` table, HNSW / GIN indexes.
- `R__campus_seed.sql`: repeatable seed of BITS Hyderabad campus services.

**Why not Java:** the schema has to be defined in the database's own language. Writing it as versioned Flyway SQL (instead of letting JPA/Hibernate generate it) gives exact control over constraints, `pgvector` HNSW indexes, `tsvector` GIN indexes and the atomic capacity guard (`points + :w <= capacity`). Java still runs the queries; SQL only defines the structure.

## 8. Shell scripts: Bash, PowerShell, Batch

**Where:**
- **Bash:** `start.sh`, `scripts/verify-m1.sh` … `verify-m6.sh` (milestone gates used in CI), `tools/setup_phase1.sh`, `tools/test_auth.sh`, `tools/test_e2e.sh`, `tools/run_test.sh`, `upload/update_github.sh`, `upload/deploy_gh_pages.sh`.
- **PowerShell:** `scripts/demo-up.ps1` (checks the demo DB, starts the backend on 8080 and Vite on 3000, waits for login), `scripts/demo-reset.ps1`.
- **Batch:** `start.bat`, `run_backend.bat`, `run_frontend.bat`, `upload/update_github.bat`.

**Why not Java:** starting processes, setting `JAVA_HOME`, calling Maven and git is what the OS shell is built for. A Java program cannot start its own JVM or the Node dev server cleanly. We keep three flavours so every team member can launch the project with one command on Linux/macOS (Bash) and Windows (PowerShell / Batch).

---

## 9. YAML, Dockerfile, Nginx config

**Where:**
- `.github/workflows/ci.yml`, `deploy-pages.yml`: GitHub Actions (JDK 21, M1 transition harness, ArchUnit tests, Pages deploy).
- `deploy/docker-compose.yml`: PostgreSQL 16 + pgvector, Mailpit, backend, frontend.
- `backend/src/main/resources/application.yml`: Spring Boot configuration.
- `deploy/Dockerfile.backend`: multi-stage Maven build on Temurin 21, then a slim JRE image.
- `deploy/Dockerfile.frontend` + `deploy/nginx.conf`: serves the built React app and proxies `/api` and `/mcp` (with buffering off for SSE) to the backend.

**Why not Java:** these are configuration formats required by the tools themselves (GitHub Actions, Docker, Nginx, Spring). They are declarative settings, not program logic.

## 10. Markdown, Mermaid, SVG, JSON

- **Markdown / Mermaid:** `README.md`, `PRD.md`, `DESIGN.md`, `PRODUCT.md`, `docs/` and the ADRs in `docs/adr/`. Mermaid renders the AI-gateway flowchart directly on GitHub.
- **SVG:** pixel-art banners, scoreboard, lifecycle map and architecture diagram in `docs/readme-assets/`, generated by `tools/readme-art/build.py`.
- **JSON:** `package.json`, `tsconfig.json`, design-reference credits and fixtures.

**Why not Java:** these are documentation and data formats, not code.

## Why not do everything in Java?

| Need | Why Java does not fit | What we used |
| :--- | :--- | :--- |
| Run code in the browser | Browsers execute JavaScript, not JVM bytecode | TypeScript / React, HTML, CSS |
| Train ML models | No mature Java equivalent of scikit-learn / skl2onnx | Python (offline only; Java runs the result via ONNX) |
| Define the database schema | Schema lives in the database; generated DDL loses control over indexes and constraints | SQL (Flyway migrations) |
| Start the JVM, Maven, Node, Docker | A program cannot launch its own runtime; that is the shell's job | Bash, PowerShell, Batch |
| Configure CI, containers, web server | Tools only accept their own formats | YAML, Dockerfile, Nginx config |
| Small API / deploy scripts beside the frontend | Needs a whole Maven project for a 50-line script | Node.js `.mjs` |

The rule we followed: **Java owns every business decision.** Every other language either renders it (frontend), stores it (SQL), builds a model that Java then runs (Python), or starts and ships it (scripts and config).
